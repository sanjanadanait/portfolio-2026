The Balance Point: Designing for Data Access at Intuit

Two years leading design across the full lifecycle of how Intuit's data workforce requests, receives, and governs access to its most sensitive data.
Role Lead Product Designer, Data Access
Timeline 2024 to 2026 (ongoing)
Scope Design owner across the full access lifecycle, spanning 10 shipped features
Partners Data Access, Data Processing, Data Lake, Legal, Compliance, Data Security, Privacy
Tools Figma, FigJam, Cursor, Claude

Overview

Every analyst, engineer, and data scientist at Intuit runs into the same problem before they can work: they need access to data, and getting it is slow, fragmented, and easy to get wrong. The data lives in different places (the data lake, feature stores, the event bus, third-party sources), in different shapes (tables, Kafka topics, ML features), under different restrictions (PII encryption, IRS 7216, SOX). Before this work, getting access meant hopping between four or more disconnected tools, filing tickets into spreadsheets, and waiting weeks, sometimes in the wrong system entirely.

What makes this a hard design space isn't the interface. It's that access is the one domain where faster-for-the-user isn't automatically the goal. Every request sits between two opposing forces: the consumer who wants access now, and the legal, compliance, and security teams whose job is to ensure the wrong person never gets the wrong data. Optimize only for the consumer and you fail the business; optimize only for control and you rebuild the wall. The real design problem is finding the balance point, and defending it to both sides.

I led design for this capability for two years, shipping ten features across the lifecycle of a request. Three principles came out of that work, and they run against how design usually works. They organize the rest of this case study.

Principle 1: Small interventions, not new tools

In most product work the deliverable is a new screen. In access, the strongest solutions were often the smallest: removing a step, or adding one small element to a flow that already existed, rather than building another tool. The hard part is knowing which single step to change, and being certain it's safe to.

Unifying four tools into one request (Real-time-data Access)

Requesting access to real-time data (Kafka topics) meant navigating four fragmented tools and could take two to three weeks. The intervention wasn't a new platform, it was folding real-time-data access requests into the table access experience users already knew. Time-to-access dropped from 2 to 3 weeks to 3 days, with 61% of requests now auto-approved.

Image coming soon: real-time-data access request within the unified table access flow
Four fragmented tools collapsed into one request surface users already knew, not a new tool.

Bringing BI-tool access to where the data is created (BI Tools Access at the Data Processing Layer)

Analysts often built the output tables themselves, joining and processing inputs in the data-processing layer, yet still couldn't explore that data in BI tools like Athena, Tableau, or QlikSense without filing a separate access ticket for each one. They'd created the table, but had to wait on three different requests just to use it. So I moved access to where the work already happened: right as they defined the output, they could pre-request access to it for whichever BI tools they'd need. The moment the table was created, it was ready to explore, no separate tickets, no tool-hopping.

Image coming soon: BI-tool access pre-requested at the point where the output table is defined
Access added at the point of work, rather than as another destination to visit.

A setting instead of a request (steward auto-approval)

Stewards were fielding manual, one-off requests to enable auto-approval for data they owned. Instead of a richer request queue, I added one steward-facing configuration surface: set preferences once, and the individual requests disappear. Approval time for internal-intent data fell from 24 hours to near-instant.

Image coming soon: Steward auto-approval configuration setting
One small configuration control removed an entire recurring request loop.

In each case the smallest intervention that satisfied both the user and governance was the right one, whether that was a new surface, a checkbox, a step, or a placement.

Principle 2: Simplify and stay compliant

The hardest both-and in this space: make it genuinely faster and easier for the user while fully satisfying compliance. When it works, the user just feels speed and never sees the governance logic underneath.

Declaring intent up front to unlock the back end (7216 Compliance Tagging)

Analysis of real request data showed compliance, specifically IRS 7216 tax-data restrictions, was the single biggest cause of denials. The move was to make compliance purpose explicit at request time by tagging roles and projects with their 7216 status and geo-restrictions. A small amount of structure up front, in exchange for eliminating 85% of previously-ineligible 7216 denials downstream.

Image coming soon: 7216 compliance tagging / geo-restriction validation
Making compliance intent explicit early removed 85% of downstream denials, simpler for everyone, without weakening the rule.

Collapsing two approvals into one (Unified Decryption Access)

Sensitive columns are encrypted, so using a table with encrypted data meant clearing two separate approvals in two different tools, the table in Discovery and then its decryption keys through an unrelated process, averaging 9 days. I unified them into a single in-flow request that lets users select the specific encrypted columns they need and provisions key access automatically on approval, while preserving column-level compliance control underneath. Time-to-access dropped from 9 days to 3.

Making the safe action easy for stewards (Revoke Access)

Earlier there was no self-serve way to revoke access at all, whether it had been granted by mistake or was simply no longer used. Stewards reached out on the support channel, which pushed the work onto our platform engineers and increased their load. Because revoking was hard, it often didn't happen, which is itself a compliance risk. I designed a self-serve revoke flow with the audit and transparency trail compliance needed, making the compliant action the path of least resistance.

A self-serve way to revoke stale or mistaken access, replacing support-channel requests that fell on platform engineers.

Principle 3: Deliberately withholding ease

The genuinely counterintuitive one, and the opposite of Principle 2: everywhere else friction is the enemy, but here sometimes correct design is making a path harder to find and harder to use, so it's used only for the cases it's meant for. Not because we couldn't make it effortless, but because effortless would be wrong.

Bulk Access, powerful but on purpose not frictionless

Bulk access lets a user request 50+ tables at once instead of one at a time, a big speedup for the right use case. The easy design would be a point-and-click UI: select tables from a list, hit request. I deliberately chose not to build that. Instead, bulk requests require uploading a CSV of table names and role ARNs, and the entry point is intentionally not placed in the most obvious, high-traffic spot.

Every one of those was a conscious decision to add just enough friction that bulk access is used for what it's for (data migrations, team ownership changes, cold starts) and not as a shortcut for everyday exploration, where it would quietly become a least-privilege and over-provisioning problem. The result still saved ~4,000 hours/year and let one customer migrate 5,000 tables in a week, proof that withholding the effortless version cost the real use cases nothing.

Image coming soon: Bulk Access CSV upload flow + note on entry-point placement
A CSV upload instead of a click-to-select UI, and a deliberately non-obvious entry point, friction placed on purpose to keep bulk access to its intended use.
The three principles aren't a sequence. They're three answers to one question: what is the smallest, most correct thing to change so both the user and governance are satisfied? The job is knowing which one a problem calls for, and defending it to both sides.

Impact across the capability

Owning design for the full lifecycle over two years meant the individual features added up to a shift in how the whole capability performed. Across ten shipped features, the work moved the numbers that matter to both sides of the balance, faster for users, tighter for governance.

Weeks → days Time-to-access dropped across the board, and to near-instant for internal-intent data through steward auto-approval.
~4,000 Operational hours saved per year through bulk access, with one customer migrating 5,000 tables in a single week.
85% Of previously-ineligible compliance denials eliminated by moving the 7216 check to request time.
61% Of topic-access requests now auto-approved after unifying four tools into one flow.
360K+ Monthly decryption key requests brought into a single governed system, built to absorb the expected 5x growth in encrypted data.
Less load Support-channel load reduced for platform engineers by replacing manual, ticket-driven paths (revoke, access states) with self-serve flows.

The throughline isn't any single metric. It's that the same body of work made access faster for users and more governable for compliance at the same time, which in this domain are usually in tension.

Reflection

01 The user is not the only stakeholder I'm designing for. In most domains, a designer can treat "what does the user want" as the north star. In access, the honest answer is that the user is one voice in a room that also holds legal, compliance, and security, and a design that ignores any of them is not a good design, no matter how clean it looks.
02 The best solution isn't always the simplest one, and it isn't always more product. Sometimes it's one small element added to a flow that already exists. Sometimes it's real speed with the governance logic hidden underneath. And sometimes it's deliberately withholding ease so a powerful path is used only when it should be. Learning to tell those apart, and to defend the call to people who each want a different outcome, is the part of this work I carried forward most directly.
03 A lot of the real design happened outside Figma. Much of the actual design happened in conversations with compliance and security rather than in a file, and being able to hold a position there, and to translate a governance constraint into a design decision and back, became as important as the screens themselves. That's the capability I've leaned on since across the rest of my platform work.
